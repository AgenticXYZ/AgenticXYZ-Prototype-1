# Prototype 1 Decision Record

This file freezes the choices that turn the development specification into an implementable release baseline.

| ID | Decision | Rationale |
|---|---|---|
| D-001 | Reference application: **Research Brief** | Small enough to inspect, rich enough to show behavior, evidence, sources, preferences, and invariants. |
| D-002 | KPR Schema version: **0.1.0** | The protocol is experimental but must be machine-readable and versioned. |
| D-003 | License: **MIT** | A short permissive license matches the repository's role as a demonstration artifact. |
| D-004 | Workspace: structured virtual files | Demonstrates change, preview, checkpoint, and rollback without arbitrary shell access. |
| D-005 | Maintainer review: claim cards plus an impact map | Keeps decisions readable while making cross-scope consequences visible. |
| D-006 | Provider: one active provider and model per run | Makes roles comparable and keeps the concept focused on policy, context, and authority. |
| D-007 | Live API keys terminate at the localhost Gateway | A key may be entered in the browser settings form, but it is sent only to `127.0.0.1`, connection-tested, cleared from the form after success, and retained only in Gateway process memory. It never enters browser persistence, exports, logs, replay fixtures, project files, or Git history. `.env.local` remains an alternative. |
| D-008 | Public static demo: Replay and Scripted modes | GitHub Pages cannot securely host user API keys or the local provider gateway. |
| D-009 | Recorded artifacts: one canonical success run plus explicit failure branches | Supports article screenshots and deterministic review without disguising recordings as live output. |
| D-010 | Old Job Talk demos are conceptual history only | Prototype 1 is a new project; old code, screenshots, and claims are not release inputs. |
| D-011 | The bundled canonical replay is labeled an **E1 reference fixture** until credentialed live capture | It exercises the same schemas and state machine without falsely claiming that a paid provider run has already been validated. A release candidate must replace or supplement it with reviewed live artifacts. |
| D-012 | Each model turn ends at one role-specific structured proposal tool | Prototype 1 demonstrates governed collaboration, not a general autonomous tool-running platform. Read context is assembled by the Runtime; application operations, human gates, and Verifiers remain explicit state-machine actions. |
| D-013 | Skills are versioned role-bound workflow definitions, not a sixth core object | Every AgentRun names its Skill; the Skill constrains purpose, allowed tools, budgets, human gates, and Verifiers without expanding role authority. |
| D-014 | Public Live replay packages omit contributor implementation references and credential availability | A reviewed run can be imported for inspection without turning local implementation evidence or local secret state into a public artifact. |
| D-015 | Codex CLI authentication is not a Provider credential | A ChatGPT-authenticated Codex session may be checked independently, but it is not reused as an OpenAI API key and cannot satisfy the Responses API Live Smoke gate. |
| D-016 | A Provider turn ends at one structured proposal; application execution is not sent back into a hidden model loop | Human gates, state transitions, Verifiers, and reruns stay visible and append-only. A successful role request is connection evidence; local health only reports configuration. |
| D-017 | Human Attestation requires explicit Contributor review, while wording correction is optional | Attestation confirms meaning and scope. A Contributor may correct any inaccurate Claim with full provenance, but accurate wording should not require a performative edit. |
| D-018 | The Reference Application publishes a machine-readable Agentic Software Contract | Manifest capabilities include side effects, permission, reversibility, failure modes, gates, surfaces, invariants, Policy approvals, and evidence requirements; synchronization tests prevent UI-only claims. |
| D-019 | DeepSeek Live uses `deepseek-v4-flash`, Thinking enabled, `reasoning_effort=high`, and strict Tool Calls | The official high-effort path supplies the real Agent capability requested for the reference demo. A DeepSeek-specific strict-schema projection improves generation reliability, while the canonical application schema remains the final authority. |
| D-020 | Provider wait is human-cancelled by default (`AGENTICXYZ_REQUEST_TIMEOUT_MS=0`) | High-effort structured proposals may legitimately take longer than a fixed local deadline. The Runtime waits for a complete response unless the person cancels; provider/tool call counts and token ceilings remain bounded, and a non-zero optional timeout is still supported and contract-tested. |
| D-021 | Release evidence uses one user-selected reference Provider; additional Provider claims are independently gated | OpenAI, Anthropic, and DeepSeek drivers all require Mock Contract coverage. Prototype 1's selected Live reference is `deepseek-v4-flash`/high. OpenAI or Anthropic may remain configurable, but neither receives a Live-support claim without its own credentialed, machine-verified, human-reviewed record. |
| D-022 | Canonical array cardinalities are repeated in the model prompt | DeepSeek strict Tool Calls omits unsupported `minItems`/`maxItems` keywords from its transport projection. The Runtime schema remains authoritative, while exact canonical bounds are derived from that schema and stated in the prompt to reduce first-call rejection without weakening validation or adding an invisible retry. |
| D-023 | Machine Live Smoke proves a human-gate transition, never an unobserved human decision | The CLI harness may exercise the full state machine with a human-labeled governance actor so Project synthesis can be verified, but its summary records `automated_test_harness` and `pending_human_review`. A real reviewer must examine and ratify or reject the staged Claim decisions before the run becomes support evidence. |
| D-024 | A reviewed Provider record keeps capture and decision as separate immutable layers | The original pending DeepSeek capture remains under `capture/` with its own checksums. The Project Maintainer's explicit approval, adopted review brief, seven Claim decisions, eight question resolutions, and evidence boundaries are recorded separately and bound by a package-level SHA-256 manifest. |
| D-025 | The workbench offers a persistent English/Chinese interface preference | Language is a local presentation preference, separate from governed project state. Switching language must not alter KPR content, authority, evidence, or Provider behavior. |
| D-026 | A persistent AgenticXYZ Guide Agent may explain, navigate, and open Provider or Runtime controls, but has no governance authority | The prototype itself must be an Agent target while preserving the distinction between Agent-centered architecture and human decision rights. The Job Talk interaction pattern informed a clean implementation; no old demo code or release claim is imported. |
| D-027 | Research Brief owns the complete KPR path; Issue Triage and Release Desk are labeled Agent-targetable previews | Multiple reference surfaces make the architecture legible and playable without pretending that every preview has complete KPR evidence or implementation. |
| D-028 | Application-only view keeps the Reference Application as the sole workbench surface while XYZ exposes the same reducer-backed workflow actions | This demonstrates software as an Agent target without forking a simplified fake flow. The view is presentation state only; KPR, Agent Run, Verifier, and human-gate state remain canonical. Human approvals still require explicit clicks. |
| D-029 | The XYZ attention helper is opt-in, exists only while the Guide is open, and places a pointer-events-free animated arrow outside the next target | Guidance should reduce uncertainty without covering or activating the control. Closing XYZ, changing the governed step, or changing view removes the pointer. |
| D-030 | Job Talk's Agent Demo and Daily News & Notes are reimplemented as interactive user-side sandboxes, not imported as old code or evidence | They preserve the useful interaction knowledge—software-directed Agent actions, cross-application preferences, capability reuse, verification, and rollback—while D-010's release boundary remains intact. Research Brief still owns the complete project-adoption reference path. |
| D-031 | A user-side application change becomes KPR knowledge only after an application checkpoint and bounded verification | XYZ may invoke allowlisted reversible capabilities, but it structures only verified need, behavior, evidence, provenance, and limitations. The local implementation remains evidence and never becomes project implementation authority. |
| D-032 | Runtime Inspector is a persistent workbench sidebar, and XYZ has one fixed bottom-right dock | Runtime remains open across workspace and application-view changes until a person closes it. XYZ never changes sides to make room for guidance; the pointer chooses a non-overlapping position instead. |
| D-033 | XYZ follows the software nesting hierarchy | Every Reference Application exposes a Local XYZ limited to that application's allowlisted capabilities and workflow. Only the outer Global XYZ may switch applications or control Provider, Runtime, views, and workbench-level navigation. |
| D-034 | Local XYZ stops honestly at its application boundary | Interactive applications may apply, checkpoint, verify, structure a bounded KPR, and roll back. Read-only previews explain their target map without simulating unsupported mutations; project decisions remain outside every Local XYZ. |
| D-035 | Each Local XYZ launcher is repositionable only inside its own application | Pointer drag and keyboard arrow movement are clamped to the application stage, stored separately per Reference Application as a presentation preference, and never alter governed project state. Dragging must not accidentally open the assistant; Home or the panel reset action restores the default position. |
| D-036 | The first three Reference Applications publish contextual preset workflows without overwriting authored intent | Selecting Research Brief, Agent Demo, or Daily News & Notes replaces the right-side request only while it is still one of the recognized system presets. Once a person edits that request, application switching preserves it and requires an explicit preset action before replacement. Each preset names its four-step path and enters the visible XYZ conversation rather than creating a hidden execution path. |
| D-037 | Reset guided demo clears governed demo state but preserves the active Provider configuration | Provider, model, Gateway availability/source, and run mode are operating configuration rather than a user or project modification. Reset reconstructs the initial guided workflow, workspaces, KPR, reference-application realizations, runs, and notifications while leaving those operating choices intact. |
| D-038 | Runtime is visible by default, while the Reference Application and User-side Agent remain a horizontal pair | Inspectability is working context rather than an afterthought. Opening or closing Runtime may resize the two user-side surfaces, but it must never reorder them into a vertical sequence. Application-only presentation still hides the workbench Runtime. |
| D-039 | The User-side Agent panel and Local XYZ Agent are two conversational entry points to the same application capability resolver and governed state | A preset or authored request may be proposed and applied directly from the right-side conversation; it never requires a handoff to the Local XYZ Agent. Opening the Local XYZ Agent afterward exposes the same checkpoint, verification, KPR, and rollback state. |
| D-040 | A reference-application KPR opens a knowledge-first review instead of leaving a draft card in the application | Creation navigates directly to KPR collaboration. The review combines intent, expected behavior, evidence, provenance, limitations, the verified local realization diff, and its rollback checkpoint; rollback invalidates the dependent draft and returns to the User Workspace. |
| D-041 | Local XYZ Agent presets are ordinary chronological conversation turns | Capability presets append the user's request and the Agent proposal to the bottom conversation composer flow. There is no second answer surface above the capability list, which keeps natural-language requests and preset requests behaviorally identical. |

Locked language:

> **Agents with People. Human in the Loop.**

> **Agent-centered, Human-governed.**
